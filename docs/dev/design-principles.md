# Design Principles

Rationale behind the rules condensed in the root `AGENTS.md`. Read this when changing an isolation boundary, a safety mechanism, the graph schema, or the relationship taxonomy.

## Graph Data Model

CrossCodex is a property-graph-first system. The compliance knowledge graph is the central data representation — every analyzer builds toward it, every query consumes from it, and every compliance report is derived from it. Understanding the graph model is a prerequisite for working on any service.

**Property graph semantics:**

CrossCodex uses a labeled property graph where nodes represent entities (controls, catalogs, artifacts, artifact types), edges represent relationships between them (REQUIRES, SEMANTIC_MATCH, DEMANDS, IS_TYPE, PARENT_OF), and key-value properties carry data about those entities and relationships (confidence scores, classification labels, temporal validity windows). Structure and data are distinct concerns:

- **Structure** is expressed by the graph topology itself — which nodes exist, which edges connect them, and in what direction. The graph engine (currently Apache AGE) manages this natively.
- **Data** is expressed by properties on nodes and edges — metadata that describes the entity or relationship, not the connection itself.

Never conflate the two. Edge endpoints are structure. Confidence scores are data. Tenant isolation is a partition key. See "Never Store Structural Topology as Data Properties" under Defensive Design Principles for the enforcement rules.

**What lives where:**

| Store | What | Why |
|-------|------|-----|
| **Property graph** (AGE) | Controls, relationships, artifacts, artifact types, compliance topology | Traversal queries, path finding, transitive closure, compliance mapping visualization |
| **Relational tables** (PostgreSQL) | Jobs, vote summaries, catalog metadata, tenant records, migrations | ACID transactions, aggregation, batch updates, operational state |
| **Object storage** (local FS / S3) | OSCAL documents, analysis results, attestations, prompt specs, CSV exports | Immutable artifacts, large blobs, reconstruction source |
| **Vector store** (pgvector) | Control embeddings, similarity matrices | Approximate nearest neighbor search, candidate pair selection |
| **Event stream** (NATS JetStream) | Audit events, work dispatch, stage notifications | Async communication, provenance, decoupled services |

The relational database and object storage are authoritative. The graph is a **materialized view** — it can be destroyed and rebuilt from the authoritative stores without data loss. Analyzers produce facts (stored as analysis results in object storage and vote summaries in relational tables), and materializers project those facts into the graph as nodes and edges. This means:

- Graph writes are idempotent. Re-materializing the same facts produces the same graph.
- Graph loss is recoverable. Re-importing the tenant's catalogs rebuilds the graph: import writes the Control nodes and queues a full analysis, whose results the graph service writes back as edges and Artifact nodes (see the upgrade note below). Replaying stored results without re-running analysis is not wired yet: the analyzer `GraphMaterializer`s that read them back have no production caller (see "Graph writers" below).
- Graph queries are read-heavy. Services query the graph for compliance topology; they do not treat it as the source of truth for raw analysis data.

**Graph writers:**

`internal/graph.Service` is the live writer of analysis facts. Its NATS subscriber hands each analyzer result event to `materialize` in `internal/graph/subscriber_handlers.go`, which writes the nodes and edges for that analyzer (SEMANTIC_MATCH, REQUIRES, DEMANDS and IS_TYPE edges; Artifact and ArtifactType nodes). The subscription is core NATS, so an event whose handler fails is not redelivered; an edge whose endpoint node is missing is therefore skipped (counted in `graph.materialize.edges_skipped.total`, see `docs/dev/telemetry.md`) instead of failing the event and losing every later edge in it, and it reappears only after the tenant's catalogs are re-imported, because import queues a fresh analysis whose events rewrite it. A skipped DEMANDS edge leaves its Artifact node, ArtifactType node and IS_TYPE edge in place, unconnected to any control (tracked in #162). Catalog ingest (`internal/catalog/service.go`) writes Control nodes and PARENT_OF edges. The `GraphMaterializer` types in `internal/analyzer/artifacts` and `internal/analyzer/relationship` write a job's nodes and edges from its results in object storage, but nothing in production calls them yet. They use their own IDs (`<control>__art_<hash>` artifacts, plain lower-case ArtifactType IDs, and the `semantic-match-rebuild` edge kind), so if one is wired into a graph that `internal/graph` also writes, the two produce separate nodes and edges for the same fact instead of one silently keeping the other's payload. The artifacts `GraphMaterializer` never replaces a stored Artifact: its artifact IDs hash only the normalized name and type, so a later job whose artifact gets the same ID with any different content (wording, confidence) is rejected, and the graph has no per-node delete to remove the stored one; keeping that job's version instead means materializing it before the conflicting job into a rebuilt tenant graph (drop and recreate it, then re-import the catalogs so the Control nodes exist; see the upgrade note below), not just re-running this materializer. Unifying the two writers is open work. `crosscodexd admin reconcile artifacts` (`internal/analyzer/artifacts.Reconcile`) writes ArtifactGroup nodes and MEMBER_OF and SAME_AS edges over the live writer's Artifact nodes; see "Artifact deduplication" below.

**Artifact deduplication:**

Artifact IDs are scoped to a control, so one real-world artifact appears as many nodes. `artifacts.Reconcile` links them in two tiers:

- **Exact tier.** Artifacts with the same lowercased `type` and `NormalizeArtifactName(name)` are an equivalence class. They join one `ArtifactGroup` node (ID `DerivedID("artifact-group", type, name)`, properties `name`, `type`) through `MEMBER_OF` edges. Because the group ID comes from content, groups never merge, split or change ID, and edges grow linearly with artifacts instead of quadratically.
- **Fuzzy tier.** Token overlap (`|A∩B| / min(|A|,|B|) ≥ 0.6`, same type) is not transitive. Matching groups therefore get one pairwise `SAME_AS` edge, from the lower group ID to the higher, and are never clustered.
  - Fields: `DeterminationType: "token_overlap"`, `Confidence` = score.
  - Properties: `similarity_score`, `matched_at`, `algorithm_version`.
  - The edge ID includes `ReconcileAlgorithmVersion`, so a rule change writes a new edge set and leaves old-version edges in place (#172).
  - The metric over-matches containment ("Policy" scores 1.0 against "Access Control Policy"), so these edges are candidates. The adjudicator (#170, below) confirms or rejects them.

Each run is stateless: it reads `Control-DEMANDS->Artifact` plus the stored `MEMBER_OF` and `SAME_AS` edges, compares in memory, and writes only missing elements with chunked `BulkCreateEdges`. Issue #91 proposed a per-node `dedup_generation` marker instead, but bumping it costs a `GetNode` plus a full `UpsertNode` per artifact, each a label-table scan in AGE (see "Why there are no indexes"). Neither Artifact writer writes it. `GraphMaterializer` accepts stored nodes that still carry the key from before #174. An edge the stored-edge query cannot see (superseded, or written concurrently) still owns its ID; `BulkCreateEdges` reports it as `ErrEdgeExists`, and the reconciler drops it and retries the rest of the chunk. A superseded MEMBER_OF edge keeps its ID forever, so every run plans it again and drops it on this same `ErrEdgeExists` path, which inflates DryRun's new-count fields. A SAME_AS pair with a closed verdict (confirmed or rejected, loaded with `ClosedPairs` and reported as `Closed`) is excluded before planning, so the adjudicator's superseded candidate edges are never re-planned and never count against MaxEdges. `Traverse` callers should pass `EdgeLabels`: a group links every artifact in it, so an unlabeled traversal from one artifact reaches all of its siblings.

**SAME_AS adjudication (#170):**

`crosscodexd admin adjudicate artifacts` (`artifacts.Adjudicator`) confirms or rejects token-overlap candidates with an LLM panel.

- **PostgreSQL is the source of truth, and the graph is a projection.** Verdicts live in `artifact_pair_verdicts` (migration 008), keyed by `(tenant_id, DerivedID("artifact-pair", low, high))` with no algorithm version, so verdicts survive #172's version bumps. AGE has no property indexes, so "find unadjudicated pairs" has to be a PG query: the reconciler enqueues every open match after its writes, and the adjudicator leases due rows with `FOR UPDATE SKIP LOCKED` in batches of `lease_batch` (default 10), each held for `lease_duration` (default 15 minutes). A pair whose lease has expired by the time its panel would start is skipped (`Expired`), because another run may hold it now.
- **A pending pair always carries the current version's candidate edge.** Re-enqueueing a pair that is still pending and automation-owned (`ON CONFLICT … DO UPDATE … WHERE status = 'pending' AND determination_type <> 'human'`) replaces only `candidate_edge_id` and `similarity_score`, keeping the context snapshot, attempts, due time and lease, so after a #172 version bump projection supersedes the new-version edge rather than the old one. `Decide` returns the stored `candidate_edge_id` (`RETURNING`) and the adjudicator projects onto that, not its leased copy, so this holds even when a reconcile re-enqueues the pair while an adjudicator holds its lease. A decided or human-owned row keeps its recorded candidate. That leaves no contradicting live edge for a confirmed or rejected pair, because the reconciler excludes closed pairs before planning and never writes their new-version edge; an `undecided` or `abandoned` pair gets the new edge and keeps the old one, both live, as its verdict projects nothing.
- **Authority ranks `human` > `llm_panel` > `token_overlap`.** `Decide` is one conditional `UPDATE … WHERE status = 'pending' AND determination_type <> 'human'`. When it matches nothing, the pair is either human-owned (the panel's opinion goes to `dissent`, and the panel writes nothing to the graph) or decided by another run (`Stale`). Human verdicts come from `crosscodexd admin adjudicate artifacts decide` (`VerdictStore.DecideHuman`, #180). One transaction locks the row by pair ref (`SELECT … FOR UPDATE`) and makes it human-owned: the status, `determined_by` = the `--reviewer` flag, confidence 1, the decision time, `graph_applied = false`, lease and last error cleared. Any state may be decided, including pending pairs, panel verdicts and earlier human verdicts; repeating the current human status is a no-op (`HumanUnchanged`, `determined_by` kept), unless a panel contradicted it afterwards (the `ReviewQueue` condition below, shared as `disputedSQL`): then it is a re-affirmation (`HumanReaffirmed`) that records the reviewer and decision time, re-queues projection and keeps the dissent, which is now older than the human verdict, so the pair leaves the review queue. Without re-affirmation a disputed pair would stay listed for good, since a reviewer who agrees with the existing human verdict would have no way to settle the dispute. An `llm_panel` verdict it overrides (confirmed, rejected or undecided) moves to `dissent` in the `dissentRecord` shape, with its evidence copied rather than decoded so an older evidence shape never blocks a human, and `evidence` is cleared; later panel dissents keep the same shape. The reviewer is not authenticated: admin one-shots trust the host, as `reconcile` and `adjudicate` do. `Enqueue`, `Lease`, `Decide` and `RecordFailure` never modify a human row (`RecordDissent` writes only its `dissent`). Projection includes human rows: `Unprojected`, `ClaimProjection`, `MarkProjected`, `ResetProjection` and `Counts.Unprojected` cover `llm_panel` and `human` verdicts, because the projection queue is how a human verdict reaches the graph. The reconciler never re-proposes a confirmed or rejected pair, whoever decided it. `ReviewQueue` (`review`) lists undecided and abandoned pairs, plus human verdicts whose dissent is a confirmed or rejected status different from the human one and decided after it; the panel verdict a human overrode is dissent too, but predates the human verdict, so an override alone does not list a pair. `SearchPairs` (`review --name`) lists pairs of any status whose `low_name` or `high_name` contains the operator's text (`ILIKE … ESCAPE '\'` with `%`, `_` and `\` escaped, so the text never acts as a pattern; validated by `ValidateSearchName`), so a panel-decided pair's ref can be found for `decide` without SQL; it scans the tenant's rows, which is fine for an admin one-shot.
- **Pair refs.** Pair keys are `DerivedID`s of group IDs, which embed untrusted, LLM-extracted artifact names: unsafe to print raw and awkward to paste. Operators address a pair by `PairRef(key)`, the first 16 hex characters of `sha256(key)`. `pairRefSQL` computes the same value in PostgreSQL (`left(encode(sha256(convert_to(pair_key, 'UTF8')), 'hex'), 16)`), so `DecideHuman` resolves a ref inside the tenant's RLS scope without a stored column. `ValidatePairRef` requires exactly 16 lowercase hex characters. No match is `ErrPairNotFound`; more than one (a 64-bit collision within one tenant, not expected) is `ErrPairRefAmbiguous`, which `decide` reports as a bug; both record nothing. Store and adjudicator errors and CLI output name pairs by ref, never by raw key; `review` also passes names, type and dissent through `CleanDisplay` (invalid UTF-8 repaired, format characters removed, control and separator runs collapsed, capped), which reuses the prompt-hardening patterns without the entity encoding.
- **Termination.** `confirmed`, `rejected`, `undecided` and `abandoned` are terminal for automation. A split panel is `undecided` because retrying a split reproduces it. A failed panel (too few valid votes; at least one is always required, so an outage never becomes a verdict) is retried with exponential backoff (`retry_base_delay`, default 1 minute, doubling up to `retry_max_delay`, default 24 hours) and abandoned at `max_attempts`. `RecordFailure` is fenced by the lease (`leased_until` must still equal the lease this run took), so a late failure from a run whose lease was taken over writes nothing.
- **System-level LLM errors stop the run.** A panel in which every call failed with a gateway, rate-limit, authentication, credential, model-allowlist or no-gateway error (`systemLLMErrors`) returns `errLLMUnavailable` without recording a failure. Recording it would spend an attempt on every leased pair and could abandon the whole queue during an outage or with a wrong key. Any other outcome, including a mix of system and other errors, is judged by consensus as usual. Pairs the stopped run leased become due again when their leases expire.
- **Prompt hardening.** Artifact names and member samples come from LLM-extracted catalog text, so they are untrusted. `promptValue` first repairs invalid UTF-8, so that removing format characters cannot splice stray bytes into a new rune such as U+202E, then removes Unicode format characters (`\p{Cf}`: zero-width, bidi and tag characters; removed rather than spaced so the model reads the visible text), collapses control and separator runs to one space, trims, caps at 200 bytes on a rune boundary and then entity-encodes `<`, `>` and `&`, so a value cannot close its tag; escaping after the cap means an entity is never split. Samples are wrapped in `<samples>` tags. The prompt is `pkg/prompt/defaults/artifact_same_as.yaml` (version 1.1.0) and resolves through the prompt registry, so operators can override it with a prompt layer. The reply parser accepts `SAME: YES|NO` only as a whole line.
- **Projection order.** `Decide` runs first, then `ClaimProjection`, the graph write and the fenced `MarkProjected` (see "Projection claims" below). A confirmation creates the `llm_panel` `SAME_AS` edge `DerivedID("same-as", "llm_panel", low, high)` (with `Supersedes` = candidate) before superseding the candidate; a candidate already superseded keeps its `valid_to`. Each run projects decided-but-unprojected rows, panel and human, at its start and again at its end, and `ErrEdgeExists` counts as success, so a crash after a graph write is completed by a later pass once its claim expires, up to `lease_duration` later; a failure before any graph write releases the claim, so the next pass retries at once. A confirmation whose groups are gone from the graph is marked projected and counted as orphaned. `Adjudicator.Project` is the same pass alone (no reset, lease or LLM); `decide` runs it right after `DecideHuman`.
- **Human projection.** `projectHuman` writes a confirmation as the edge `DerivedID("same-as", "human", low, high, FormatTime(decided_at))` (`DeterminedBy` = reviewer, `DeterminationType` `human`, confidence 1, `Supersedes` = candidate, `ValidFrom` = decision time). The decision time is in the ID so that a reversal followed by a re-confirmation, or a re-affirmed confirmation, writes a fresh edge instead of colliding with its own superseded one; a re-affirmation supersedes the previous human edge at its decision time. Both verdicts then `Traverse` depth 1 outbound over `SAME_AS` from low and supersede every live edge to high except that edge: the candidate, older-version candidates of an undecided pair, an `llm_panel` edge (including one a racing run wrote after an earlier pass of this verdict) and an earlier human edge. Edges with `valid_to` set are skipped, because `SupersedeFact` overwrites `valid_to` unconditionally and re-superseding would rewrite history; this also makes two passes projecting one verdict write the same `valid_to`. Each edge is superseded at the decision time or at its own `valid_from` if that is later, so a reviewer clock running behind the adjudicator's never ends an edge before it began. `ErrEdgeExists` is success; `ErrNodeNotFound` counts as orphaned and marks the row projected, as for the panel.
- **Projection claims and the fence (#180).** Every projection, panel or human, is claim → write → release, recorded in `projection_claimed_until` (migration 008). `ClaimProjection` is one conditional `UPDATE` that sets the claim to now + `lease_duration` where the row still holds the projection (determination type, status, `decided_at`), is not `graph_applied`, and has no live claim (`IS NULL OR <= now`). `ClaimAcquired`: write. `ClaimReplaced`: a newer verdict replaced this one; write nothing, count `Fenced`, and the pass loops because the newer verdict is queued. `ClaimBusy`: another live claim holds it or it is already projected; write nothing, count `Busy`, the claimant finishes it. `MarkProjected` is the fence: it acts only where `projection_claimed_until` equals the caller's own claim, clears the claim, and sets `graph_applied` to whether the row still holds the projected verdict; `false` counts `Fenced` and leaves the newer verdict queued, and a claim that expired and was taken over is left alone. `ReleaseClaim` clears the caller's claim after a failure before any graph write; after a write that may have landed the claim is kept until it expires, so a newer verdict is projected after that write. `DecideHuman`, `Decide` and `ResetProjection` never change a claim; `DecideHuman` reports a live one in `HumanDecision.ClaimedUntil`, which `decide` prints. `Unprojected` hides rows under a live claim, so a pass never spins on a row another pass holds. Claims last `lease_duration`, the existing "how long one worker may hold a pair" knob rather than a new one, so the config loader validates it even when adjudication is disabled. There is no advisory lock: the graph never shares a PostgreSQL transaction with relational queries, so no PG lock can span the graph write, while a claim row outlives transactions and expires after a crash. Amendment 10 (panel `Decide` applies, a human decides, the panel writes its edge) resolves in every order. The human commits before the panel claims: the claim is `ClaimReplaced` and the panel writes nothing. The human commits while the panel holds the claim: the human projection skips the row; the panel's `MarkProjected` finds a newer verdict and leaves it queued, and the run's end-of-run pass (or a later `decide` or run) supersedes the panel edge. The human commits after `MarkProjected`: the panel edge already exists, and the human projection's live-edge scan supersedes it. The panel crashes between its write and `MarkProjected`: its claim expires and the next pass projects the human verdict over the panel edge. Remaining window: a projection that outlives `lease_duration` minus the clock skew between hosts can be overtaken by another pass, and a graph write it makes after that pass read the graph is not undone; `--reproject` repairs it. Claims and leases are judged on caller clocks, so hosts must be NTP-synced. A host whose clock runs far ahead holds its claim that far into the future; `--reproject` does not clear claims, so clearing one early takes a manual `UPDATE` setting `projection_claimed_until = NULL` on that tenant's row.
- **Data lifecycle.** `artifact_pair_verdicts` is a permanent per-tenant record of who decided what and why: it is never deleted, including when its tenant is deleted. `app_user` has no `DELETE` grant on it, and it sits outside per-job retention (`purge_user` has no grant on it either). There is no retention policy for the table (#190): it holds only the latest verdict per pair, so nothing superseded accumulates, and the `evidence` justifications are the only explanation of the current graph state. Rows are never deleted, but a row is updated in place: `DecideHuman` overwrites `status`, `determined_by`, `confidence`, `evidence` (set to NULL) and `decided_at`. When a human overrides an `llm_panel` verdict, that verdict's status, confidence, adjudicator, `decided_at` and stored `evidence` are copied into `dissent`; a later panel opinion on the human-owned pair (`RecordDissent`) replaces `dissent`. When a human re-decides a pair another human decided, the earlier reviewer and decision time are overwritten and `dissent` is left as it was, so the database keeps no copy of the earlier human verdict: `identity_events` records only tenant and reviewer actions and holds no verdict history. The LLM audit log keeps call history under its own `audit_llm` tier. Do not set `evidence` to NULL on an `llm_panel` row: `Unprojected` refuses such a row, so it could never be projected again, even with `--reproject`. Migration 009 (#195) enforces this: `BEFORE DELETE` and `BEFORE TRUNCATE` triggers on `artifact_pair_verdicts` and on `tenants` refuse the change for every role, the table owner included; the verdicts' foreign key to `tenants` is `ON DELETE RESTRICT`; and `app_user` lost `DELETE` and `UPDATE` on `tenants`. Only the owner or a superuser can get past the triggers, by disabling them or by setting `session_replication_role = replica`. That rests on a stated assumption: migrations run as the owner, and no application role (`app_user`, `graph_user`, `tenant_admin`, `backup_user`, the retention roles) owns these tables or is a superuser. Tenants and reviewers are retired by soft delete instead; see [Identity Lifecycle](#identity-lifecycle).
- **Expect tokens.** `decide` requires the `EXPECT` token `show` printed: a hash of the pair's status, determination, `determined_by`, confidence, `decided_at`, similarity score, `evidence` and `dissent`. `DecideHuman` checks it under the row lock and refuses (`ErrPairChanged`) when another reviewer or a panel changed the pair since it was viewed, so nobody overwrites a verdict they never saw. Queue and projection bookkeeping (attempts, leases, `last_error`, `graph_applied`, claims) is excluded so background work never invalidates a token. A pair already holding the same undisputed human verdict is accepted as unchanged whatever the token, so re-running a decide whose projection failed still completes it.
- **Rebuilds.** A rebuilt graph loses the projected edges, and the reconciler does not re-plan closed pairs. Run `crosscodexd admin adjudicate artifacts --tenant <tenant> --reproject`: it resets `graph_applied` on the tenant's `llm_panel` and `human` confirmed and rejected verdicts (`VerdictStore.ResetProjection`) and re-projects them in the same run, without leasing pairs or calling the LLM.

**Graph partitioning:**

Each tenant gets its own graph instance named `crosscodex_{tenant_id}`. Tenant isolation at the graph level is structural — queries execute within a single graph, and cross-tenant traversal is impossible by construction. This is enforced by each driver: `pkg/graphdb/agedriver` prepends the tenant-scoped graph name to every Cypher query, and `pkg/graphdb/memdriver` keeps one in-memory graph per tenant.

**Suspension** is enforced at the gateway, not in storage. After authentication, the Connect auth interceptor calls `tenant_is_active()` (migration 007) for unary and streaming RPCs, and refuses a tenant that is suspended or has no `tenants` row with `PermissionDenied`. A failed lookup refuses with `Unavailable` (fail closed). Health is exempt. Queued pipeline work, retention, backup and reconcile keep running for a suspended tenant, so its data stays manageable. The check runs only when the gateway `Service` has an authn registry; the standalone `gateway` role currently builds none, so it does not enforce suspension. The check is one `tenant_is_active()` query on the app pool per non-health request or stream, uncached, so a suspension takes effect on the next request. A pool exhausted under load surfaces as `Unavailable`. A deleted tenant fails the same check, since `tenant_is_active()` requires `status = 'active'`. Unlike suspension, deletion is also enforced in storage: `enter_tenant` refuses a deleted tenant on every app path, so its queued pipeline work is refused too (see [Identity Lifecycle](#identity-lifecycle)).

**Driver contract and temporal encoding:**

Every `graphdb.GraphDB` driver honors the contract documented on the interface and enforced by `internal/testspecs.GraphDBContractBehavior` (run against `memdriver` in unit tests and `agedriver` in integration tests). Edges require both endpoints to exist exactly once, node IDs are unique across labels within a tenant's graph (a second label returns ErrNodeIDConflict), non-empty edge IDs are unique (`ErrEdgeExists`), every derived edge ID (REQUIRES, semantic-match, semantic-match-rebuild, demands, is-type, parent-of) is built with `graphdb.DerivedID` and a leading kind tag (for example `graphdb.DerivedID("requires", job, source, target)`), and `BulkCreateEdges` is all-or-nothing. Together these make re-materialization idempotent.

**How agedriver serializes writes.** AGE has no unique constraints on property values, so agedriver enforces node-ID uniqueness and idempotent graph creation with transaction-scoped PostgreSQL advisory locks (`pg_advisory_xact_lock`, which the restricted `graph_user` may call without a grant; PostgreSQL releases the lock at commit or rollback). `CreateNode` and `UpsertNode` lock `advisoryKey("node", graph, id)`, so writers for one ID wait for each other whatever their labels; `CreateGraph` locks `advisoryKey("graph", graph)`, a separate key domain. The locks work only because `beginTx` pins every transaction to READ COMMITTED: the existence check that runs after a wait takes a fresh snapshot and sees what the previous holder committed, which a REPEATABLE READ snapshot taken before the wait would miss. Edge writes take no lock, so concurrent writers can still create two edges with one non-empty ID. The contract clause is on `graphdb.GraphDB` (`pkg/graphdb/interface.go`); the mechanism is `lockNode`, `CreateGraph` and `beginTx` in `pkg/graphdb/agedriver/client.go`.

A derived node or edge ID that joins more than one variable part goes through `graphdb.DerivedID` unless every part but one is drawn from a fixed alphabet that cannot contain the separator; then the separator found from that side splits the ID back into its parts, so distinct inputs cannot collide. Current examples of that exception: artifact node IDs `<control>__art_<n>` (`internal/graph/subscriber_handlers.go`, decimal index) and `<control>__art_<hash>` (`internal/analyzer/artifacts/materializer.go`, fixed-width hex), and catalog Control node IDs `<catalogID>/<itemID>` (`internal/catalog/service.go`, where `catalogID` is 16 hex characters). `graphdb.DerivedID` percent-escapes `%` and `_` in each part and joins the parts with `_`. Control IDs come from tenant catalogs and can contain `_`, so plain joining would let distinct pairs share an ID and the second edge would be dropped as a duplicate. Escaping keeps `_` a pure separator, so distinct non-empty part lists always get distinct IDs (the empty list and `[""]` both give `""`, so callers always pass a kind tag first); parts without `_` or `%` read unchanged (`requires_job-9_ac-2_ac-1`).

agedriver's isolation depends on caller text never reaching SQL. One database role owns every tenant graph, so nothing below the driver stops a statement from reading another graph. Each Cypher query is embedded in SQL inside a `$cypher$ ... $cypher$` dollar-quote, and three rules keep caller text where it belongs. Labels and property keys are spliced into Cypher unquoted, so every driver rejects any that fail `graphdb.CheckIdentifier` (`[A-Za-z_][A-Za-z0-9_]*`). Values are escaped and have the tag stripped repeatedly, because one pass can rebuild it from its halves. `ExecuteQuery` rejects caller-written Cypher that contains the tag instead of rewriting it. The tenant is spliced into the SQL itself, outside the dollar-quote, as the graph name `'crosscodex_<tenant>'`, so every driver rejects a tenant that fails `graphdb.CheckTenant` (`tenant.ValidateTenantID`: 3-52 lowercase letters, digits and hyphens) instead of trusting callers to have validated it. The 52-character cap is 63 minus `len("crosscodex_")`: PostgreSQL truncates identifiers to 63 bytes, so without it two tenant IDs sharing a 52-character prefix would map to the same graph. Separately, written `Properties` may not use a key the driver writes itself from a `Node` or `Edge` field (`id`, `valid_from`, `valid_to`, ...; `confidence` on edges only, because nodes carry a caller-set `confidence`; see `graphdb.ReservedNodeKeys` and `graphdb.ReservedEdgeKeys`): such a key would override the field, for example replacing `Edge.ID` after the `ErrEdgeExists` check ran. Query property filters may still use reserved keys.

**How bulk writes work.** agedriver has no property indexes, so every lookup by `id` is a sequential scan of all label tables. `BulkCreateEdges` checks a whole batch with one or two queries: `n.id IN [...]` for the endpoints, plus `e.id IN [...]` when any edge has an ID. It then creates the batch with one `UNWIND` statement per edge label, matching endpoints with `WHERE s.id = r.s` so PostgreSQL hash-joins the rows against a single vertex scan. A batch costs a fixed number of scans instead of several per edge. The graph RPC caps batches at `graph.max_bulk_edges` because AGE evaluates a long literal list in worse than linear time.

**Why there are no indexes.** Indexes were tested on AGE 1.5 / PostgreSQL 16. An index on a label's own table is used: a GIN index on `properties` serves `{id: 'x'}`, and an expression index on `agtype_access_operator(VARIADIC ARRAY[properties, '"id"'::agtype])` serves `n.id = 'x'` and `n.id IN [...]`. An index on the parent `_ag_label_vertex` / `_ag_label_edge` does not cover the label tables that inherit from it. AGE creates label tables lazily inside a Cypher `CREATE`, and that does not fire `ddl_command_end` event triggers, so neither a migration nor the `tenant_graph_create` trigger can index labels that do not exist yet. `graph_user` owns its label tables and could create indexes without new grants, but that would put DDL on the write path: `CREATE INDEX` takes a SHARE lock that blocks writers, concurrent first writers race, and the expression form depends on how AGE translates property access internally. Adding indexes reliably needs explicit label creation (`ag_catalog.create_vlabel` / `create_elabel`) together with the index, behind a driver API that callers invoke before writing.

Temporal properties (`valid_from`, `valid_to`, `analyzed_at`) are stored with `graphdb.FormatTime`, a fixed-width UTC layout (`2006-01-02T15:04:05.000000000Z`) whose lexical order equals chronological order. AGE compares these strings in Cypher, so the width matters.

> **Upgrade note (#148):** graphs written before this encoding used RFC3339Nano, which trims trailing zeros. Old and new encodings do not compare correctly, older REQUIRES edges have no `id` or `valid_from`, and derived edge IDs changed format (see `graphdb.DerivedID`): SEMANTIC_MATCH, DEMANDS, IS_TYPE and PARENT_OF IDs always differ, and REQUIRES IDs differ when a job or control ID contains `_` or `%`. Older graphs can also hold one node ID under two labels; edges to such an ID fail as an "ambiguous node ID", and CreateNode or UpsertNode under the other label returns ErrNodeIDConflict. Re-materializing into an old graph adds a second copy of each such edge instead of deduplicating it. No automated rebuild command exists yet; rebuilding an affected tenant's graph from the authoritative stores is a manual process:
>
> 1. Drop the tenant's graph (e.g. `SELECT ag_catalog.drop_graph('crosscodex_{tenant_id}', true)`). This drops only the graph; the `tenants` row and its relational data stay.
> 2. Recreate it with `graphdb.GraphDB.CreateGraph` (idempotent — safe even if the graph already exists).
> 3. Re-import each of the tenant's catalogs (`crosscodex catalog import <file>` or `crosscodex run start <file>`) so control nodes and `PARENT_OF` edges exist again; catalog ingest (`internal/catalog/service.go`) is the only place that creates them, never the analyzer materializers.
> 4. Catalog import queues a full-analysis job automatically; let it run to completion so the graph service (`internal/graph/subscriber_handlers.go`) recreates the `SEMANTIC_MATCH`, `REQUIRES`, `DEMANDS`, and `IS_TYPE` edges from the new results.
> 5. Once the analysis jobs finish, run `crosscodexd admin reconcile artifacts --tenant <tenant>` so the rebuilt graph regains its `ArtifactGroup`, `MEMBER_OF` and `SAME_AS` elements, then run `crosscodexd admin adjudicate artifacts --tenant <tenant> --reproject` to re-project its SAME_AS verdicts.
>
> The graph is still a materialized view, so no data is lost — but step 4 re-runs the LLM-backed analyzers from scratch rather than replaying already-stored results, so expect it to take as long (and cost as much) as the original analysis.
>
> **Tenant IDs longer than 52 characters (#148):** `pkg/tenant` now rejects them, so every request and message carrying such an ID fails validation, and so does config load when one appears as `tenants.default_tenant` or as a key under `llm.tenant_overrides`, `attestation.tenant_overrides`, `prompt.tenant_overrides` or `synthesis.tenant_overrides`. Their graphs were also never isolated: `create_tenant_graph()` truncates `'crosscodex_' || tenant_id` to PostgreSQL's 63-byte identifier limit, so two such tenants sharing a 52-character prefix share one graph. Find affected tenants as the `postgres` superuser (the `tenants` RLS policy hides every row from `app_user`):
>
> ```sql
> SELECT tenant_id, length(tenant_id) FROM tenants WHERE length(tenant_id) > 52;
> ```
>
> A tenant ID cannot be renamed in place: nine tables reference `tenants(tenant_id)` without `ON UPDATE CASCADE`, and copying rows between tenants is exactly the manual fix the isolation rules forbid. Re-provision instead:
>
> 1. Choose a replacement ID that passes `tenant.ValidateTenantID` (3-52 characters) and does not equal the first 52 characters of any existing `tenant_id`. `crosscodex_<those 52 characters>` is already a graph name — the old tenant's truncated graph, created by `create_tenant_graph()`'s own truncation of `schema_name` — so inserting a tenant whose graph name collides makes `ag_catalog.create_graph` fail inside the `tenant_graph_create` trigger, and the insert (and the restart in step 2) fails with it.
> 2. Set `tenants.default_tenant` to it, and rename the tenant's keys under every `tenant_overrides` map (config load rejects an invalid `default_tenant` and the old keys anyway). Only role `all` provisions the tenant: `attachAllGateway` (`cmd/crosscodexd/bootstrap.go`) calls `db.EnsureTenant`, whose insert fires `tenant_graph_create` and creates the new tenant's graph. Restart `crosscodexd` with role `all` to pick up the change. Role `pipeline`'s `buildPipelineService` (`cmd/crosscodexd/bootstrap.go`) only checks that `default_tenant` is set — it does not provision anything — so a split-role deployment that never runs role `all` must provision the tenant with `crosscodexd admin tenant create --tenant <new-id> --display-name <name>` (connects as the least-privilege `tenant_admin` role; see `deploy/README.md`).
> 3. Re-import the tenant's catalogs under the new ID and let the queued analysis jobs finish, as in steps 3-4 above. Do not reuse the old graph: it may hold another tenant's data.
>
> The old tenant's rows stay in place. Nothing can read them, because every service rejects the old ID. Tenants are never hard-deleted: since migration 009, triggers refuse `DELETE` and `TRUNCATE` on `tenants` for every role and the `tenant_graph_drop` trigger is gone (see [Identity Lifecycle](#identity-lifecycle)). `crosscodexd admin tenant delete` validates `--tenant` with `tenant.ValidateTenantID`, so it cannot soft-delete an over-long ID either; the old rows remain as an inert record. Its truncated graph `crosscodex_<52-character-prefix>` also remains, and every tenant sharing that 52-character prefix was writing into it. Drop it by hand with `ag_catalog.drop_graph` only after confirming no other tenant still depends on it — dropping destroys the shared graph outright.

**The relationship-type taxonomy is a starting point, not a closed standard:** `pkg/config/validate.go`'s `validRelationshipTypes` and `internal/analyzer/relationship/types.go` currently enumerate the 8 NIST IR 8477 relationship types (EQUIVALENT, SUPERSET_OF, SUBSET_OF, CONTRIBUTES_TO, COMPLEMENTS, PARTIAL, CONFLICTS_WITH, NO_RELATIONSHIP). These are CrossCodex's current set, not an immutable external constraint — expand the enum when a real relationship concept doesn't cleanly fit the existing 8 values. Weigh that against keeping the new concept outside the enum entirely (see `internal/synthesis.ConsensusRequires`, which treats the `requires` analyzer's consensus label as a distinct, always-actionable signal rather than folding it into this taxonomy) based on whether it's genuinely a peer of the existing relationship types or a structurally different kind of signal.

The long-term direction is broader than NIST IR 8477: CrossCodex is expected to eventually support the relationship and attribute surface of **ReqIF** (Requirements Interchange Format) and **SysML v2 Requirements** structures, not just compliance-control relationships. Don't design the relationship/attribute model as if the current 8-value enum or today's control-oriented properties are the final shape — keep node/edge property schemas (see the table above) and the relationship-type enum easy to extend rather than hard-coding assumptions that only fit compliance catalogs.

## Identity Lifecycle

Judgements are permanent, so the identities behind them are never removed: migration 009 (#195) makes tenants and reviewers soft-deletable, lets a deleted one be hidden behind a pseudonym an admin can trace, and records every change in an append-only, signed audit log. Every change runs as `tenant_admin` through a `SECURITY DEFINER` function in `pkg/db/migrations/009_identity_lifecycle.up.sql`; the Go API is `db.TenantAdmin` (`pkg/db/identity.go`) and the CLI is `crosscodexd admin tenant delete|restore|hide|unhide`, `admin reviewer add|list|delete|restore|hide|unhide` and `admin identity trace` (`cmd/crosscodexd/admin_identity.go`).

| Identity | From                     | Command                     | To                                | Function                                         |
|----------|--------------------------|-----------------------------|-----------------------------------|--------------------------------------------------|
| tenant   | `active` ⇄ `suspended`   | `tenant suspend` / `resume` | `suspended` / `active`            | `set_tenant_status` (refuses `deleted`)          |
| tenant   | `active` or `suspended`  | `tenant delete`             | `deleted`                         | `delete_tenant`                                  |
| tenant   | `deleted`, not hidden    | `tenant restore`            | `suspended`                       | `restore_tenant`                                 |
| tenant   | `deleted`                | `tenant hide` / `unhide`    | `deleted`, hidden / shown         | `hide_tenant` / `unhide_tenant`                  |
| reviewer | unregistered or `active` | `reviewer add`              | `active`                          | `add_reviewer` (upsert; refuses `deleted`)       |
| reviewer | `active`                 | `reviewer delete`           | `deleted`                         | `delete_reviewer`                                |
| reviewer | `deleted`, not hidden    | `reviewer restore`          | `active`                          | `restore_reviewer`                               |
| reviewer | `deleted`                | `reviewer hide` / `unhide`  | `deleted`, hidden / shown         | `hide_reviewer` / `unhide_reviewer`              |

- **Restore lands in `suspended`.** Restoring makes a tenant's data reachable again, so the operator re-activates it as a separate, deliberate step (`admin tenant resume`). `set_tenant_status` refuses a deleted tenant, so only `restore_tenant` leaves `deleted` and the audit log's delete and restore events stay paired. `provision_tenant` refuses to rename a deleted tenant. A reviewer has no suspended state, so a restored reviewer is `active`.
- **Pseudonyms.** On the first hide the database generates `hidden-tenant-<16 hex>` or `hidden-reviewer-<16 hex>`: the first 64 bits of `sha256` over a random UUID (`sha256`, not `md5`, so it works under FIPS), unique per table. It is kept on unhide and restore and reused on the next hide, so old reports stay traceable. A hidden tenant is listed by its pseudonym with an empty display name. The `hidden-` prefix is reserved for tenant and reviewer IDs (`tenants_id_not_reserved`, `reviewers_id_not_reserved`), so output never shows a real ID that looks like a pseudonym; migration 009 refuses to apply, changing nothing, while a tenant ID or a human verdict's reviewer already uses it.
- **Reviewers of a deleted tenant.** `add_reviewer` and `restore_reviewer` are refused, since they would make a reviewer usable again; both take `FOR SHARE` on the tenant row so `delete_tenant` waits for them. `delete_reviewer`, `hide_reviewer` and `unhide_reviewer` stay allowed, so a deleted tenant's reviewers can still be retired and concealed.

**`enter_tenant` is the storage gate.** `public.enter_tenant(id)` replaces `set_config('app.current_tenant', …)` on every `app_user` and `graph_user` path: `db.NewTenantPool`'s `Begin`, agedriver's tenant scoping (`pkg/graphdb/agedriver/client.go`) and the hand-scoped transactions in `internal/pipeline`. It refuses a deleted tenant with SQLSTATE `42501` (fail closed) and enters an unknown tenant as before, so RLS matches zero rows. Like the suspension check it takes no lock: a transaction that entered before `delete_tenant` committed may finish, and every later one is refused. Retention is the one exception: a deleted tenant's job data still follows retention, so it scopes through `db.NewRetentionTenantPool` instead (see [retention.md](retention.md)). The spec "never sets app.current_tenant directly outside retention" (`pkg/db/enter_tenant_bdd_test.go`) scans every non-test Go file in the repository and fails on a direct scope statement anywhere but `pkg/db/tenant_pool.go`, `pkg/retention/purge.go` and `pkg/retention/archive.go`.

**Reviewer registry.** `reviewers` (per tenant, under RLS; `app_user` has `SELECT` only) lists who may record human verdicts. Like `tenants`, it has triggers (`reviewers_refuse_delete`, `reviewers_refuse_truncate`) that refuse `DELETE` and `TRUNCATE` for every role; a reviewer is retired with `delete_reviewer`. Registration is explicit (`admin reviewer add`); migration 009 registered every reviewer of an existing human verdict with `created_by = 'migration-009'`. `PGVerdictStore.DecideHuman` first calls `require_active_reviewer`, which refuses an unregistered (`P0002`, mapped to `ErrReviewerNotRegistered`) or deleted (`55000`, `ErrReviewerDeleted`) reviewer and locks the reviewer row `FOR SHARE` until commit, so `delete_reviewer` cannot run while that reviewer's verdict is being recorded. It is a definer function because `FOR SHARE` needs `UPDATE` privilege, which `app_user` must not have. It reads the tenant from `app.current_tenant` and trusts it exactly as RLS does, so it reveals nothing `app_user` cannot already `SELECT`. Residual risk: `app_user` can `set_config` another tenant and hold `FOR SHARE` on that tenant's reviewer row, delaying its `delete_reviewer` until the transaction ends. Because a direct `set_config` skips `enter_tenant`, the function re-checks that the tenant is not deleted. The deleted-reviewer error leaves out the reviewer ID: it reaches span status, and the reviewer may be hidden.

**Hiding is view-level.** It changes what `list_tenants`, `list_reviewers`, `list_retention_tenants` and the verdict store's `DisplayBy` (printed by `adjudicate artifacts show` and `decide`) return; nothing is rewritten. The raw ID still appears in `artifact_pair_verdicts.determined_by`, readable by any role with `SELECT` on it, `app_user` included; in `Edge.DeterminedBy` on human `SAME_AS` graph edges; in `reviewers.reviewer_id`, which `app_user` can read for its tenant; in `identity_events`; and in retention audit records and NATS subjects. Hiding conceals an identity from routine output; it is not erasure. Failed `db.TenantAdmin` spans carry only a coarse status, so operator input stays out of traces (see [telemetry.md](telemetry.md)).

**Audit log.** `identity_events` is append-only: no role holds any privilege on it, so only the definer functions (running as the owner) write it and only the owner reads it, and triggers refuse `UPDATE`, `DELETE` and `TRUNCATE`. A row holds `action`, `kind`, `tenant_id`, `identity_id`, `actor` (`--by`), `reason`, `db_user` (`session_user`), `request`, `attestation` and the generated `attestation_sha256`. `request` is the request's canonical JSON (`db.IdentityRequest.Canonical`); `attestation` is an in-toto link named `identity.<action>`, signed with `attestation.private_key_path`, whose single material `crosscodex:identity-request` has `sha256(request)` as its digest. The CLI refuses before touching the database when the keys or `database.tenant_admin_dsn` are missing. The database does not check the signature (it has no key). It checks the binding: `record_identity_event` refuses a request whose `action`, `actor`, `reason` and `identity_id`, and `kind` and `tenant_id` except on a trace, differ from the change, so a request signed for one identity cannot be replayed against another. A trace request names the pseudonym, with `kind` and `tenant_id` empty, while the row records the resolved identity; an unknown pseudonym records nothing. Size caps: `actor` 1-256 bytes and `reason` 1-500 bytes of printable text, `request` at most 4096 bytes, `attestation` non-empty and at most 65536 bytes.

To verify an event, as the owner:

```sql
SELECT event_id, occurred_at, action, kind, tenant_id, identity_id, actor, reason,
       request, attestation, attestation_sha256,
       encode(sha256(request), 'hex') AS request_sha256
FROM identity_events
WHERE tenant_id = 'acme'
ORDER BY event_id;
```

1. Verify the `attestation` envelope's signature with the attestation public key (`attestation.Generator.Verify` in `pkg/attestation` does this).
2. Check that the link's `crosscodex:identity-request` material digest equals `request_sha256`. Hash the stored `request` bytes; never re-encode the JSON, since only `IdentityRequest.Canonical` reproduces those bytes.
3. Check that the request's fields match the row as described above. `attestation_sha256` matches an exported envelope to its row.

**Rollback and tests.** `009_identity_lifecycle.down.sql` refuses while any tenant is deleted or `identity_events` holds any row, because the audit log is as permanent as the judgements; export and remove those rows deliberately as the owner first. Integration-test cleanup cannot delete tenants either, so it uses `dbtest.HardDeleteTenantSQL`: a superuser statement under `session_replication_role = replica`, which skips the refusal and foreign-key triggers and is acceptable only for disposable test databases.

## Defensive Design Principles

These principles apply to all packages, not just database code. They reflect hard-won decisions about how CrossCodex handles failure, isolation, and human error.

### Fail Closed, Not Open

When a safety mechanism is absent or misconfigured, the system must deny access rather than grant it. Examples:
- If `app.current_tenant` is not set, RLS policies match zero rows (not all rows).
- If a graph name can't be derived, the query fails with an error (not a fallback graph).
- If an extension is missing at startup, the service refuses to start with a clear error.

Design every isolation boundary so that the default state — before any configuration — is "deny all."

### Errors Must Be Actionable

Every error a human can trigger must tell them: what happened, why it was blocked, and what to do instead. This applies to database triggers, API responses, CLI output, and log messages. A tired operator at 2am should be able to read the error and know their next step without consulting documentation.

Bad: `ERROR: permission denied`
Good: `ERROR: cannot modify job abc123: status is "completed". To retry, create a new job instead of resetting this one.`

An error whose detail would expose internals still has to be actionable, but without that detail. A graph RPC whose error maps to `CodeInternal` does not return driver or database text (SQL and Cypher fragments, SQLSTATE codes, internal graph names) to the client (CWE-209). The client gets a fixed message that says what to do: retry, and if the failure persists, give the operator the trace ID it names (or the time and method name when there is no trace). `rpcError` in `internal/graph/service.go` logs the full error server-side once, with the method and trace ID, so the operator can find the cause. Errors the client can fix (not found, invalid argument, reserved property key) keep their detailed message.

### Verify the Negative Path

Every safety mechanism needs a test that proves it works by attempting the forbidden operation and asserting three things:
1. The operation returned an error (not silent success).
2. The error message is actionable (contains enough context to diagnose).
3. The data is unchanged after the failed operation (the error wasn't raised but swallowed).

Skipping step 3 is how silent data corruption ships.

### Threat Model: Tired Admin at 2am

Design guardrails assuming the adversary is not a malicious attacker but a well-intentioned operator making reasonable-seeming manual interventions under pressure. Test for:
- Bulk operations that hit a mix of protected and unprotected rows (must fail entirely, not partially).
- Attempts to disable safety mechanisms (triggers, RLS) via direct SQL.
- Privilege escalation through operations the application role shouldn't have (TRUNCATE, ALTER, COPY).
- Manual "fixes" like resetting a completed job's status or reassigning rows between tenants.

The system should make the wrong thing hard and the right thing obvious.

### Privilege Separation

Application code runs under a restricted database role, not the table owner. The table owner (superuser) bypasses RLS and can disable triggers. This is PostgreSQL's design, not a bug — but it means:
- Tests must use the restricted role to verify isolation, not the superuser.
- GRANTs must be explicit and minimal (SELECT, INSERT, UPDATE, DELETE — not TRUNCATE, not ALTER, not TRIGGER).
- Comment in the codebase WHY the restricted role exists, because the next person will be tempted to simplify by using the superuser for everything.

### No Partial Success on Safety-Critical Operations

When a batch operation (UPDATE, DELETE) touches rows with mixed protection states (some completed, some not), the entire statement must fail — not silently succeed for the unprotected rows. PostgreSQL's per-row BEFORE triggers provide this guarantee, but tests must verify it explicitly because it's the kind of behavior that breaks silently if someone refactors triggers into rules or policies.

### Prefer Discovery Over Hard Coding

When practical, code should discover what to load and how to load it instead of hard coding it. If a value is likely to vary across deployments, document types, or user preferences, expose it as configuration with a sensible default — do not bury it in source code where only a developer can change it.

This applies to thresholds, keyword lists, regex patterns, format allowlists, chunk sizes, retry counts, and any other tuning parameter. The test: would a user deploying CrossCodex against a different compliance framework need to change this value? If yes, it must be configuration, not code.

### Configuration Surface Discipline

Every runtime-configurable knob in a package MUST have a corresponding config field in `pkg/config` OR a documented wiring contract explaining how it gets its value. No silent knobs — if a functional option exists but has no config field, the gap must be caught during review.

Rules:
- **No orphan options:** If a package exposes `WithX(val)`, there must be a config field that feeds it, or a doc comment on the option explaining the wiring contract (e.g., FIPS mode derived from `tls.fips.enabled`).
- **Naming fidelity:** Config field names must match the semantic meaning of the value they configure. If the package expects a public key PEM file, the config field is `public_key_path`, not `cert_path`.
- **Per-tenant completeness:** If a config section supports `tenant_overrides`, every field that could reasonably differ between tenants must be overridable. If a field is intentionally global-only, document why.
- **Deduplication:** Do not create a second config knob for a value that already has a canonical source. Example: FIPS mode is `tls.fips.enabled` — attestation, storage, and future packages derive it from there rather than adding their own `fips_mode` field.
- **Validation coverage:** Per-tenant overrides must undergo the same validation rules as their global counterparts (e.g., key path pairing, positive durations).
- **Test coverage:** Every config field must have tests covering: default value, valid override, and invalid value rejection with actionable error message.

### Upsert Over Reject When Data Is Sound

When receiving valid data that conflicts with an existing record by identity (same ID, same tenant), prefer upsert (insert-or-update) over rejection. Failing with "already exists" forces the caller to implement delete-then-insert or check-then-branch logic that is both fragile and race-prone. If the incoming data passes validation, the caller's intent is clear: this is the current truth, store it.

This applies to controls, catalogs, embeddings, configuration records, and any other entity where re-import or incremental update is a reasonable operation. Reserve "already exists" errors for cases where duplication genuinely indicates a bug (e.g., two controls with the same derived ID within a single import batch).

Graph nodes and edges are a deliberate exception. `CreateNode` rejects a duplicate label and ID with `ErrNodeExists` (and an ID already used under another label with `ErrNodeIDConflict`, which no writer treats as success), and `CreateEdge` rejects a duplicate non-empty edge ID with `ErrEdgeExists`; both keep the stored element, because the graph is a rebuildable materialized view. `internal/graph`, the live writer, treats `ErrNodeExists` and `ErrEdgeExists` as success. The analyzer `GraphMaterializer`s (no production caller yet; see "Graph writers") do too, except that the artifacts one first checks that a stored node matches and reports a mismatch. For edges whose ID includes the job (REQUIRES, SEMANTIC_MATCH) a duplicate from the same writer carries the same payload; the two SEMANTIC_MATCH writers use different kind tags, so they never collide. Edges whose ID has no job (DEMANDS, IS_TYPE, PARENT_OF) are shared across jobs: the stored edge keeps the first writer's `determined_by` and `confidence`, and later jobs do not change them. The live writer's Artifact nodes are shared the same way: `internal/graph` derives an Artifact ID from the control and the artifact's position in the result list (`<control>__art_<index>`), with no job and no content in it, and treats `ErrNodeExists` as success. A later analysis job that returns a different artifact at the same position for a control therefore leaves the first job's name, type, confidence and `job_id` on that node, and the DEMANDS edge to it is the existing one. Changed artifacts from a re-analysis appear only after the tenant's graph is rebuilt (see the upgrade note above), so "re-materializing the same facts produces the same graph" holds for the same facts, not for revised ones. Graph nodes written by catalog ingest use `UpsertNode` instead: a `Control` node projects a control row that ingest has just upserted, so re-importing a catalog refreshes the node's title, statement and other properties in place (its `PARENT_OF` edges stay attached) instead of leaving the first import's text, while the node keeps the `valid_from` of its first import, so `AsOf` traversals of earlier times still see it. `UpsertNode` replaces the caller-owned properties, so a property the new import no longer sets is removed, and it keeps the `SupersedeFact` state (`valid_to`, `superseded_by`) unless the caller sets `ValidTo`. A catalog ID is a hash of the document content and tenant, so an edited document becomes a new catalog with new nodes; only a re-import of the same bytes (for example after a parser change) reaches the existing nodes. A fact that changes is recorded with `SupersedeFact` and a new edge, never by updating an edge in place.

### Graph Backend Portability

The graph database (currently Apache AGE) is accessed exclusively through the `pkg/graphdb.GraphDB` interface. No package outside `pkg/graphdb` may import AGE-specific types, use AGE SQL functions directly, or assume the graph shares a PostgreSQL transaction with relational queries. The graph is a materialized view — reconstructible from authoritative stores (see "Graph Data Model" above). Design every graph consumer so that swapping AGE for Neo4j, Neptune, or any openCypher/Gremlin backend requires changes only inside `pkg/graphdb/agedriver` (or a new sibling sub-package).

### Never Store Structural Topology as Data Properties

In a property graph, edges ARE the structural connection between nodes. The endpoints of an edge (which nodes it connects) are topology, not data. Never duplicate this structural information as key-value properties on the edge.

**Anti-pattern (do not do this):**
```go
// WRONG: source/target stored as data properties on the edge
edge := graphdb.Edge{
    Label:      "REQUIRES",
    Properties: map[string]any{"source": "AC-1", "target": "AC-2"},
}
client.CreateEdge(ctx, tenant, edge)
```

**Correct pattern:**
```go
// RIGHT: source/target are parameters that define which nodes the edge connects
edge := graphdb.Edge{
    Label:      "REQUIRES",
    Properties: map[string]any{"confidence": 0.95},
}
client.CreateEdge(ctx, tenant, "AC-1", "AC-2", edge)
```

This principle extends to any value that is already expressed by the graph structure:
- **Edge endpoints** — encoded structurally by `(source)-[edge]->(target)`, never as edge properties
- **Tenant ID on edges** — already the graph partition key (graph name `crosscodex_{tenant_id}`), never redundant as an edge property
- **Node identity** — the `id` property on a vertex is its lookup key, not duplicated elsewhere

On the read side, edge endpoint identity comes from the `Relationship` struct's `Source` and `Target` `Node` fields (populated by the MATCH pattern's `s` and `t` columns), not from edge properties.
