# Authorize NATS clients by certificate identity

## Context and Problem Statement

The compose `nats` service runs with `--tls --tlsverify` and no authorization rules (`deploy/compose.yaml`). It authenticates a client as "holds a certificate the deploy CA signed with clientAuth", and then grants that client unrestricted publish and subscribe on every subject, including JetStream management. Issue #298 asked whether NATS should also authorize by client identity, for example by restricting publish and subscribe to the daemon's `client` identity.

What the stack looks like after #298:

- Only one clientAuth certificate exists: `client.pem` (CN `client`). Server certificates are serverAuth-only and per service, so no server key can act as a NATS client.
- `client-key.pem` is mounted only by `migrate` and `crosscodexd`. The same `client.pem` is the daemon's identity to PostgreSQL, NATS and the LLM gateway, and the operator's CLI identity.
- Tenant isolation on NATS is subject-level and enforced by the application (`pkg/tenant.ValidateTenantID`; AGENTS.md: per-tenant NATS accounts are not implemented). NATS permissions can restrict which subjects a client may use, but they do not know about tenants.
- Split roles (`pipeline`, `graph`, `worker`, `gateway`) can run as separate containers but today share the one client certificate.

The question is whether adding NATS-side authorization now buys isolation the stack lacks.

## Decision Drivers

- **Real isolation gained.** A rule that every legitimate client already satisfies adds configuration, not protection.
- **Blast radius of a compromised role.** A worker that can publish to any subject can forge stage-completed or barrier events other roles act on.
- **Operability.** Added config must be generated, mounted and kept in step with the subject layout (`crosscodex.<class>.<tenant>.<job>...`, `pkg/natsbus/subjects.go`).
- **Fail-closed behavior and brittleness.** Mapping a certificate to a user depends on the certificate subject; a formatting or re-issue mismatch locks the daemon out.
- **Existing safety.** The compose network is the trust boundary; the CA key is on the host only.

## Considered Options

- **Option A: Keep authentication only (status quo).** Any CA-signed client certificate has full access.
- **Option B: Authorize the single `client` identity.** Add an `authorization` block to a mounted `nats.conf`, with `verify_and_map: true` so the certificate subject picks the user, and give that user publish and subscribe on `crosscodex.>`, `_INBOX.>` and `$JS.API.>`.
- **Option C: Defer, and authorize per role once roles have their own client certificates.** Issue one clientAuth certificate per role (`gateway`, `pipeline`, `graph`, `worker`), map each with `verify_and_map`, and give each only the subjects it publishes and subscribes to.

## Decision Outcome

Chosen: **Option C (defer; adopt when per-role client certificates exist)**, because Option B protects nothing the stack does not already protect, and Option C is where NATS authorization starts to pay. The maintainer accepted the deferral on 2026-11-22. No option is implemented; revisit when per-role client certificates exist.

### Consequences

- **Positive:**
  - No `nats.conf` to generate, mount and keep in step with subject names, and no new way to lock the daemon out of its own bus.
  - The decision is tied to a trigger, not to a calendar: the work becomes worthwhile when the first of these lands.
- **Negative:**
  - Until then, a holder of `client-key.pem` (the daemon, `migrate`, anyone who copied the operator's CLI identity) has full NATS access. A compromised `crosscodexd` already holds the database credentials and the attestation key, so NATS adds little beyond that for the single-daemon stack.
  - In a split deployment, a compromised worker can publish on subjects it should only consume.
- **Triggers to revisit:**
  - Split roles are deployed with separate containers, so a role's compromise should not grant the others' subjects. This is the main one.
  - A second client certificate for a different purpose (an operator, an integration) is issued from the same CA.
  - Per-tenant NATS accounts are taken up (AGENTS.md says they are not implemented); account-level isolation would replace much of the subject-level trust in the application.
- **What adopting Option C needs:** a `nats.conf` generated by the deploy tooling from the role list; `verify_and_map` with a pinned certificate subject per role (so `gen.go` must put the role in the CN or an OU); per-role allow lists derived from `pkg/natsbus/subjects.go`; a smoke assertion that a role is refused on another role's subjects (positive control first, as the existing NATS probe does); and a README "Upgrading" note because each role's client certificate changes.

## Pros and Cons of the Options

### Option A: Keep authentication only (status quo)

- Good, because it is what the stack runs and tests today, with nothing to maintain
- Good, because the only clientAuth certificate is held by `migrate` and `crosscodexd`, and the CA key is not in any volume
- Bad, because a compromised role can publish or subscribe anywhere, including subjects of other tenants
- Bad, because every future client certificate from the CA is trusted as fully as the daemon

### Option B: Authorize the single `client` identity

- Good, because it is a small change and documents the intent that only the daemon talks to NATS
- Good, because it refuses a CA-signed certificate with another subject, should one ever be issued
- Bad, because every legitimate client presents that same certificate, so it removes no capability from any of them
- Bad, because the daemon, `migrate` and the CLI share the identity, so the rule cannot tell them apart
- Bad, because `verify_and_map` ties access to the exact certificate subject; reissuing the certificate with a different subject locks out the daemon, and the failure shows up as a connection error at start-up
- Bad, because it needs a mounted config file and an allow list that must follow `pkg/natsbus` subject changes

### Option C: Per-role client certificates with per-role permissions

- Good, because it limits the blast radius of a compromised role to that role's subjects
- Good, because the allow lists can be derived from the subject constructors the code already has
- Bad, because it multiplies client certificates (and the places they are mounted) and changes the PKI layout and the README "Upgrading" notes again
- Bad, because per-role subject lists must stay in step with the code, which needs a test that fails when a role publishes a subject its list omits
- Bad, because it only matters once roles run separately, so it is work with no payoff for the single-daemon compose stack
